## What Hakam is (30-second version)

Hakam is a **firewall that lives inside the Linux kernel**. Instead of being a
program that watches traffic from the outside, parts of it run *inside* the
kernel itself, right where packets and system calls happen. It's built to be
shown at **Black Hat Arsenal** (a security conference), so the whole project is
organised around a roadmap (`docs/arsenal_roadmap.md`) with numbered features
and deadlines.

A few terms that come up constantly:

- **eBPF** — a way to safely run small programs *inside* the Linux kernel. The
  kernel has a "verifier" that refuses to load any eBPF program it can't prove
  is safe (no infinite loops, no reading random memory). "Passing the verifier"
  is the recurring hurdle.
- **XDP** — an eBPF program that runs the instant a network packet arrives, the
  earliest possible point. Hakam uses it to inspect and drop packets.
- **BPF-LSM** — an eBPF program attached to a "security hook" inside a system
  call. Hakam uses it on `connect()` (the call a program makes to open a network
  connection) so it can *deny the connection before it even happens*.
- **conntrack** ("connection tracking") — keeping a little table of the active
  network connections so you can remember things about each one.
- **the VM** — eBPF only builds and runs on Linux, but this work happens on a
  Mac. So there's a Linux virtual machine called `hakam` (via OrbStack) where
  everything is actually built and tested. The Mac drives it remotely.

We never push to GitHub — all work is committed **locally** only.

## Part 1 — Reviewing the project before continuing

We started by reviewing the codebase to find problems before adding new
features. The review found that a feature called **#6 (BPF-LSM connect
enforcement)** had been written but not committed, not tested, and had a few
issues. The findings were written up in `docs/phase2_review_2026-06-29.md`.

The most important issue: the code *claimed* to be "per-process" enforcement,
but it actually wasn't. It blocked connections based on the **destination**
(where you're connecting *to*), not based on *which program* is connecting. We
fixed the wording so the claim matches reality — important because at the
conference, experts will ask hard questions and any exaggeration hurts
credibility.

We also added a safety check to the pre-demo script (`preflight.sh`) and a test
(`smoke.sh`) and fixed a documentation file to match the code.

## Part 2 — Proving feature #6 actually works

Feature #6 is supposed to **block a program from opening a network connection
to a forbidden address**. Talking about it isn't enough — we proved it live in
the `hakam` VM:

1. We told Hakam to block the address `1.2.3.4`.
2. From a normal terminal we tried to connect there with three different tools
   (`curl`, `python3`, `nc`).
3. All three were **denied instantly** with the error "Operation not permitted"
   — and the denial happened in **0 milliseconds** (meaning no network packet
   was ever sent; the connection was stopped before it started).
4. As a control, connecting to a *different*, non-blocked address still worked —
   proving Hakam blocks only what you tell it to, not everything.

That was the proof feature #6 works. We then committed it and marked it done in
the roadmap's progress tracker.

**A note on the confusion that happened here:** Hakam has *two* different
prompts. One is Hakam's own command line (where you type `policy-block`), and
the other is a normal Linux terminal (where you type `curl`). Typing `curl` into
Hakam's prompt does nothing — they're different things. That tripped us up
briefly; the fix was just "use a second terminal for normal commands."

## Part 3 — Starting feature #7 (the big one)

With #6 done, the only remaining headline feature is **#7: the eBPF conntrack**
(the connection-tracking table). We first wrote a detailed plan
(`docs/phase2_7_conntrack_plan.md`) and then started building it in small,
safe steps, testing and committing after each one.

### Why #7 matters (in plain terms)

When data is sent over the network, it's broken into pieces called **segments**.
An attacker can hide an attack by splitting it across two segments — each half
looks innocent on its own. Hakam already stitches segments back together to
catch this. But it had two weaknesses:

1. If segments arrive **out of order** (common on the real internet), the
   stitched-together result is scrambled and the attack can slip through.
2. The network sometimes **re-sends** a segment ("retransmit"). Hakam would
   stuff the duplicate into its buffer, wasting space.

To fix both, Hakam needs to know each segment's **sequence number** (a counter
TCP puts on every segment saying where it belongs in order). Feature #7 builds a
small table in the kernel that tracks this per connection. Here's what we did,
step by step.

### Step "flow-types foundation"

We defined the **shape** of the data: a `FlowKey` (the four things that identify
a connection: source address, destination address, source port, destination
port) and a `FlowState` (what we remember about each connection: the next
expected sequence number, a timestamp, a packet count). We also created the
kernel table itself, `CONNTRACK`, which auto-forgets the oldest connections when
it gets full (so it can never run out of memory and crash). Verified with tests.

### Step "xdp-observe"

We made the XDP program (the one that runs on every arriving packet) read each
segment's **sequence number** and record the connection into the `CONNTRACK`
table. **This was the riskiest moment of the whole feature** — the kernel
verifier might have rejected the new code. We tested it by loading Hakam onto a
spare network interface in the VM, and it **loaded successfully on the first
try**. That removed the single biggest risk in the plan.

### Step "seq-on-the-wire"

The kernel sees *every* segment, but the part of Hakam that does the
stitching (in userspace) only sees *some* of them. So the kernel is the only
one that can correctly judge whether a segment is **in order**, a **duplicate**,
or **out of order (a gap)**. In this step the kernel makes that judgment and
attaches a little label to each segment it passes up. Verified: tests pass and
the verifier still accepts the program.

### Step "userspace-dedupe"

We taught the stitching code to **use those labels**:

- A segment labelled "duplicate" → **thrown away** (no more wasted buffer
  space).
- A segment labelled "out of order" → counted (so we can see how often it
  happens) and, for now, still kept so we never lose real attack data.
- A segment labelled "in order" → added normally.

We added tests proving a duplicate is dropped and an out-of-order segment is
counted. The whole project rebuilt and all tests passed.
