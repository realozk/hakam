## #10 — Driver-mode XDP  ✅ (with one honest asterisk)

Background: Hakam's packet filter can attach to the network at two levels — a
generic/slow spot ("SKB mode") that works everywhere, or a fast spot inside the
network driver ("driver mode"). All the demos so far used the slow spot. A
reviewer will ask "is that all you've got?"

Today we **proved driver mode works**: attached Hakam in driver mode to a virtual
network device and confirmed it loaded natively (not the slow path). So it's not
SKB-only.

The one thing we **can't** do in a VM is publish *honest real-hardware speed
numbers* — a virtual machine's networking is too artificial to represent a real
network card, and faking a number would be worse than none. That single item (a
benchmark run on a physical box with a real NIC) is the accepted leftover; the
benchmark harness for it already exists in `bench/`, so it's a "run it on
hardware" task, not a "build it" task. Marked done with that noted.

## #11 — Attack replay corpus  ✅

We built a "clone → replay → watch it block" demo:
- **4 real attack captures** (`corpus/pcaps/`): a SQL-injection, a cross-site
  scripting attempt, a path-traversal, and a command-injection-style request.
- **A replay script** (`scripts/replay-corpus.sh`) that re-sends each captured
  attack at a running Hakam and checks that each one is blocked.

We ran it: **all four were blocked**, each correctly identified.

One honesty point we baked in: the "command injection" capture is actually caught
because it contains `/etc/passwd` (a file-access signature), not because Hakam has
a dedicated command-injection detector — it doesn't. We documented it as what it
truly is rather than overclaim coverage.
