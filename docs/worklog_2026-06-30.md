## What "running the core" means here

Hakam's core is the firewall itself — the kernel programs plus the controller
program (`hakam-node`) that loads them and prints what's happening. Today's work
is about packaging that core so it starts cleanly on a fresh machine.

## Step 1 — Fix the "dies with no keyboard" bug

We found this yesterday: the program shut itself down the instant its keyboard
input ended. Fine for a person typing in a terminal, fatal for a server, a
container, or a system service (none of which have a keyboard attached).

The fix: the program now checks whether it has a real terminal.
- **With a terminal** → interactive command line, as before.
- **Without one** → "headless mode": it skips waiting for typed commands, prints
  a short notice, and keeps running — doing its actual job (filtering traffic,
  serving its live data feed) until told to stop.

We were careful to make it also **stop cleanly** when asked, so a service manager
or `docker stop` doesn't hang waiting for it. Verified in the VM: it stays up
headless, serves its data feed, and shuts down cleanly on the stop signal.

This was the keystone — nothing else in Phase 3 works until the program can run
without a terminal.

## Step 2 — Run it as a system service (systemd)  ✅ tested

We added the files that let a Linux machine run Hakam as a managed background
service:
- An installer script that builds everything and puts it in the right places.
- A service definition so you can do `systemctl start hakam` / `stop hakam`.
- A small config file where you set which network card to watch.

We **installed and ran this for real** in the VM: started the service (it came
up, armed all its kernel hooks, served its live feed), then stopped it (it
detached everything cleanly). This path is solid.

## Step 3 — Run it in a container (Docker)  ✅ tested

We wrote the files to run the core as a container (build recipe, startup script,
one-line run command), then **installed Docker in the VM and actually built and
ran it**:

- The image **built successfully** — including the notoriously fussy `bpf-linker`
  step we were worried about (~10 min; final image 166 MB).
- `docker run` brought the whole core up: it armed all its kernel hooks, ran
  headless, and served its live data feed.
- The real proof: we fired a SQL-injection request at a target and the
  **container's datapath blocked it** — so the packaged container genuinely
  filters traffic, it doesn't just start.
- `docker stop` shut it down cleanly, detaching every hook (exit code 0).

So both deploy paths — system service and container — are now proven end-to-end.

## The "UI is optional" principle, made concrete

Everything we shipped today installs and runs **the core only**. The dashboard
app is documented as an optional extra you can attach afterward by pointing it at
the core's live feed — and the deployment guide leads with "you don't need it."
